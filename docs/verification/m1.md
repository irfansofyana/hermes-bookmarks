# M1 integration evidence

This is evidence for a development foundation, not full M1 acceptance or a v1 release. The implementation snapshot is the commit containing this document; the earlier review-fix baseline is `5ea392075f18799bf5d9e8c0a0167f047acd8092`.

## Real host, not a router double

A disposable conventional HOME/HERMES_HOME was created under scratch. Only this plugin's source/delivery files were copied there, its shared library root was configured using `hermes config set`, and it was enabled using `hermes plugins enable`. The official PM prepared dependencies only for that disposable home. No active configuration, installed plugin, vault or user credentials were copied.

Real `hermes serve --isolated --host 127.0.0.1 --port 0` and `hermes dashboard --isolated --skip-build --no-open` processes used that home. They were managed independently of the user's services. Session tokens were minted for the fixture in mode-0600 files and are never part of this repository. The test clients used actual TCP, authentication middleware, plugin-host registration, namespace routing, image decoding, and storage.

| Check | Observed result |
| --- | --- |
| Initial backend smoke | 15 checks passed, exit 0: status, plugin health, capture/read, duplicate identity, raw image download, upload metadata and decoded preview |
| Unauthorized requests | Item GET, item POST and owned-asset GET returned 401 without the fixture token |
| Stop/restart and reopen | Old port closed; a fresh process read the same saved item and image; 10 restart checks passed, exit 0 |
| Cross-process native read | Actual Hermes plugin manager and `model_tools.handle_function_call` read the HTTP-created item through `bookmark_get`; returned the same ID |
| Native invalid capture | The actual registry invocation of `bookmark_save` rejected `file:///not-authorized` with `invalid_url`; no job was created |
| Cold owner worker | Actual probe initially failed: synchronous registration reported `host_loop_unavailable`, leaving a deliberately unconfigured job pending |
| Worker fix | Public async native-tool/API activation now starts it with `ctx.spawn_task`, without creating a loop. After the HTTP request returned, the real worker consumed a new deliberately incomplete job and persisted `failed / configuration_required`, exit 0 |

The worker probe used an explicitly synthetic, non-callable route (`fixture-no-inference` / `not-a-real-model`) and incomplete job settings to stop before publisher extraction or model invocation. It proves supervised activation and persistent queue progress, **not** a working provider or generated summary. No synthetic provider response was passed off as real output. Real model trust, routing, text and vision calls remain unverified and require approval.

The activation fix retains only the registered public context, its profile identity, and lifecycle-owned metadata in the plugin's own bridge. Only that profile can activate its context. Native handlers are registered with public `is_async=True`; native capture and authenticated API entry bootstrap on the host's existing async lane. No private host imports, host-loop introspection, custom daemon, independent event loop or replacement scheduler were added to production code. Bootstrap can resume previously accepted automatic jobs, including when a configured library is first opened; a GET-only health/smoke probe is not a promise of zero background processing.

## Real Dashboard UI

The built, served Hermes Dashboard loaded the committed Dashboard bundle through its actual SDK. No SDK shim, replacement React root or fake HTTP service was used. Verified:

- Capture and image upload/preview against the real backend.
- Live Hermes Teal to Nous Blue theme change; an unsaved URL and the uploaded preview survived.
- 1280×1000 and 390×1000 viewports in each theme. Four unique screenshots were recorded; measured page and plugin horizontal overflow were false in all four.
- Keyboard Tab from URL input reached Save link.
- A deliberately aborted browser POST exercised the failed-save state: URL retained, then an actual backend retry succeeded. That was explicit network-fault injection, not a fabricated successful response.
- No browser `pageerror` was reported during the successful interaction run.

Screenshots: `screenshots/dashboard-{dark,light}-{1280,390}.png`. Contact sheet: `screenshots/dashboard-themes.png`. Content, URLs and image pixels are synthetic fixtures. The phone captures show the top of the scrollable library; content below the fold was not represented as missing.

## Desktop acceptance remains blocked

The packaged Desktop executable was launched on a disposable Xvfb display with separate HOME, HERMES_HOME, Electron userData, application identity and isolated-backend settings. Its actual userData path was read back and matched the fixture, so the active Desktop was not used. The session's advertised bot display was unavailable; the scoped Xvfb process avoided the user's display.

The disposable app remained offline behind its connection overlay, including a retry with the documented dependency-complete Python override. It opened the native shell/settings but did not reach a usable connected bookmark page or mounted native composer. It was closed afterward. This is an environment/target acceptance failure, not proof of a plugin defect or permission to patch Hermes, bypass the overlay, edit private renderer state, or touch the active app. Desktop rendering/handoff remains covered only by emitted-entrypoint/public-SDK-shaped tests. Dashboard's inspected SDK still has no supported editable native context/draft handoff; the action remains unavailable there.
